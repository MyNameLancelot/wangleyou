# SDD 维护指南

SDD 让有行为或架构影响的变更具备范围、验收、验证和基线同步。长期规则见 [AGENTS](../AGENTS.md)；本指南补充记录字段、检查方式和清理约定，不替代语义审查或浏览器验收。

## 文档职责与流程

| 文档 | 记录内容 |
| --- | --- |
| [requirements](requirements.md) | 当前产品范围与验收行为 |
| [architecture](architecture.md) | 系统组织、边界、依赖及真实实施状态 |
| 各模块 `module.md` | 目的、职责/非职责、公开输入输出、依赖、状态/资源、主要文件、扩展与验证 |
| [decisions](decisions/README.md) | 仍有维护价值的技术选择、候选方案和取舍 |
| [README](../README.md) | 使用、开发、内容维护、构建与分发步骤 |
| [changes](changes/README.md) | 本次或尚未完成变更的范围、任务和实际证据 |

先检查代码、文档、活动任务、最近提交和用户改动，再按影响建立记录；实施前明确范围与计划，范围变化先更新记录。改变已确认范围须先取得用户同意，常规细节自行决定并记录。验证后同步受影响基线，再审查差异、链接和证据；不能以 CI 通过代替语义正确。

恢复工作继续现存任务，不重建已完成计划。多项活动变更分别标明模块和依赖，不擅自合并；未决事项写明决策时点，失败或必要验收受阻时保持未完成。

## full 与 light

| 模式 | 适用影响 | 必需文件 |
| --- | --- | --- |
| full | 用户行为/验收、数据结构、模块职责/接口/依赖、关键状态或资源生命周期、具有产品或架构影响的构建部署 | `change.json`、`spec.md`、`plan.md`、`tasks.md` |
| light | 无行为或架构语义变化的文案/排版/维护，或恢复明确既有规格的局部修复 | `change.json` |

判断实际影响，不以行数、扩展名或“bug”标签豁免。新页面、流程、交互/组件语义、主题、重要响应式、空状态或错误恢复必须 full。纯文档整理若不改变需求、验收或工程边界，可使用 light。

full 规格记录问题、目标、非目标、行为、边界和编号验收项；计划记录影响模块/页面、依赖顺序、实施/验证/回退方式；任务用勾选项反映真实状态。用户可见要求以最新已确认口述为准，写进规格与验收，以指定视口的实际浏览器流程核对，不维护 Penpot 或其他外部设计稿。

## change.json 字段

每个 PR 必须新增或更新 `docs/changes/<名称>/change.json`，多个声明共同覆盖整个 PR。实施前建立，范围变化同步，提交前填实际验证。

| 字段 | 要求 |
| --- | --- |
| `mode` | `full` 或 `light` |
| `summary`、`reason` | 实际修改范围与原因；light 说明为何不改变行为/架构 |
| `behavior`、`architecture` | 布尔值，任一 true 必须 full |
| `verification` | 非空字符串数组，只填已经执行的命令/结果、核对证据及明确未执行范围 |
| `impacts` | 逐项声明 `requirements`、`architecture`、`modules`、`decisions`、`readme` |
| 各 impact 的 `status`、`reason` | `updated` 或 `none`，均说明原因 |
| `updated` impact 的 `paths` | 非空仓库相对路径数组，必须出现在本次差异中；删除文档也需明确声明 |

不使用 `designImpact`、`designReason` 等设计分级字段。声明和计划可按需要增加说明，但不能代替实际基线更新。活动记录可作为字段结构参考，但其验证是历史证据，不能套用为新变更的结果。

## 依赖与自行实现评估

具有一定复杂度的通用能力，先检查项目已有实现/依赖，再检查平台能力和维护活跃的成熟库。合适则优先复用，不为简单逻辑机械增加依赖，也不重复实现成熟能力。

在本次记录中简述候选方案、选择和理由：关注生命周期适配、模块边界、维护状态、许可证、运行时/构建体积、版本兼容、静态/子路径/WebView 限制、降级和验证成本。重要长期取舍另写 ADR，精确依赖版本以锁文件为准。

主题 UI、CSS、装饰和资产完整归主题目录，主题间禁止互导；只有无 UI 类型、纯领域逻辑和交互契约可以共享。唯一共用 UI 例外是 `media-viewer`：主题只挂载，不覆盖样式/功能或复制实现。当前只有 book 主题，无主题切换。

## 检查与证据

```sh
npm run check:sdd -- --worktree --base origin/main
npm run check:sdd -- --staged
npm run check:sdd -- --base origin/main
npm run check:sdd -- --structure
```

工作区检查含未提交及未跟踪文件；staged 检查索引；base 检查已提交差异；structure 只检查模块结构。PR CI 使用完整差异检查。工具验证声明、Markdown 相对文件链接和模块公开入口/依赖方向，不验证锚点、声明真实性、交互语义或全部动态依赖。改文件时同时核对未改文档对它的引用。

使用 Node 24/npm 和对应锁文件。常用 `npm run check`、`npm run build`、`npm run test:e2e`，实际命令见 README；新增/修改命令同步 README。验证与影响相称，纯文档变化重点检查链接、声明与语义，无需为排版增加测试。

行为变化重点验证内容边界、播放状态和资源清理，浏览器使用静态产物并覆盖仓库子路径；记录浏览器版本、视口、操作及结果，视口模拟、原生模拟器和真机分开。失败、未运行和不可用如实写明，不虚构通过，不以机械测试或无依据覆盖率替代行为验证。

提交前核对：范围与验收一致；状态/资源唯一归属及清理明确；必要基线已同步；主题隔离、媒体路径和模块边界未漂移；证据和链接可追溯。提交使用中文 Conventional Commit：`type(scope): 中文描述`，类型保留英文，正文按需说明原因与验证。分支保护及合并权限以仓库 Settings 为准。

## 活动记录与完成清理

`docs/changes` 保留正在修改或仍有本次必要验收待办的活动记录，入口由目录 README 维护。完成后先把有长期价值的行为、契约和取舍同步到基线，再移除已完成过程记录；不把截图、设计稿、完成计划或旧版本验证快照当作长期基线。历史可从 Git 查阅，不另建重复档案。

仍有活动实施或本次必要验收受阻时保留 full 文件及真实未完成状态，不能为清理目录而勾选完成。已合并交付的旧版本记录或用户已暂缓的非活动计划，经用户要求核实清理时，可将仍有效的验证缺口、未交付状态和恢复条件移入基线后删除历史目录；这只是记录退役，不等于验收通过或取消需求。后续规则取代旧要求时说明证据适用版本；早期通过不自动证明现版本通过。

清理前检查引用、待办和仍有效证据；清理本身也要有覆盖该差异的 change.json。正在交付的 PR 保留自己的声明，后续清理再移除已完成记录；不在同一 PR 删除唯一声明，也不让长期基线依赖已完成计划。
